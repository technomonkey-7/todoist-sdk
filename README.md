# Todoist SDK

Unofficial Todoist API clients for TypeScript, Python and Go, with a CLI and an MCP server, generated from Doist's OpenAPI definition.

Todoist is a task manager. Its API v1 covers tasks, projects, sections, comments, labels, reminders and workspaces over REST, with cursor-paged lists.

Learn more about Todoist API at [developer.todoist.com](https://developer.todoist.com).

This is an unofficial SDK for the Todoist public API, generated by Arda Çankaya with [`@voxgig/sdkgen`](https://github.com/voxgig/sdkgen). It is not affiliated with, endorsed by, or sponsored by the upstream API provider.

> TypeScript, Python, Golang SDKs, a CLI with an interactive REPL, and an MCP server for AI agents — all generated from one OpenAPI spec by [@voxgig/sdkgen](https://github.com/voxgig/sdkgen).

> **Features:** `paging`, `retry`, `test`, `timeout` — opt-in,
> inactive until switched on, and configured per client. See the Features
> section of any SDK README below for what each one does.

## About Todoist API

These clients are generated by [Voxgig's SDK generator](https://github.com/voxgig/sdkgen) from the OpenAPI definition Doist publishes for the Todoist API v1, used unmodified (see `.sdk/def/PROVENANCE.md`). Doist maintains official SDKs for TypeScript and Python; this repository adds Go, a command-line tool and an MCP server, all from the same definition. Doist has not reviewed this project, and Todoist is a trademark of Doist.

### Try it offline

```bash
git clone https://github.com/technomonkey-7/todoist-sdk
cd todoist-sdk/ts
npm install
npm run build
npm test
```

The test suite needs no account or network: each SDK has a test mode that replaces the HTTP transport with an in-memory mock.

### Authentication

Create a personal API token in Todoist under Settings, Integrations, Developer. Pass it as `apikey`; the SDK sends it as `Authorization: Bearer <token>`. The CLI and the MCP server read it from `TODOIST_APIKEY`.

### Work with tasks

```ts
import { TodoistSDK } from '@technomonkey-7/todoist-sdk'

const client = new TodoistSDK({ apikey: process.env.TODOIST_APIKEY ?? '' })

// A task with no project_id goes to the Inbox. The cast is needed because the
// generated create type requires every field of a task record (see Honest state).
const task = await client.Task().create({ content: 'Write the release notes' } as any)

// Item verbs are actions on update; search and filter are actions on list.
await client.Task().update({ id: task.data().id, $action: 'close' })
await client.Task().update({ id: task.data().id, $action: 'reopen' })

const inbox = await client.Task().list({ project_id: task.data().project_id })
console.log(inbox.map((t) => t.data().content))

await client.Task().remove({ id: task.data().id })
```

Every call above was run against the live API (see Honest state).

### Using the MCP server

```bash
cd go-mcp && go build -o todoist-mcp .
export TODOIST_APIKEY=<token>
claude mcp add --scope user todoist -- "$PWD/todoist-mcp" -transport stdio
```

The server registers `todoist_list`, `todoist_load`, `todoist_create`, `todoist_update` and `todoist_remove`. The last three change your Todoist data when an agent calls them; sdkgen leaves them off by default and this project turns them on. To build a read-only server, set `main: kit: target: 'go-mcp': tool: write: false` in `.sdk/model/project.aontu` and regenerate.

### Coverage

34 entities cover 105 of the 108 operations in Doist's definition. Task, Project, Section, Comment and Label have `load`, `list`, `create`, `update` and `remove`, with item verbs (`close`, `reopen`, `move`, `archive`, `unarchive`) as update actions and `search`/`filter` as list actions. Left out: `POST /revoke`, `DELETE /access_tokens` and `POST /access_tokens/migrate_personal_token`, which need an OAuth application's client secret. The corrections to how the generator reads the definition are in `.sdk/model/guide/guide.aontu`, each with its reason.

### Honest state

Generated on 2026-10-15 with create-sdkgen 0.30.7, @voxgig/sdkgen 4.34.7 and @voxgig/apidef 8.25.2, on Windows. Not production-tuned; use it as a starting point.

Verified against the live API with a personal token: create, load, list, update and remove for Project, Task, Section, Comment and Label, and Task close and reopen, through the TypeScript SDK; reads across the API through the generated live suites in TypeScript, Python and Go; `list`, `load` and `update` through the CLI; `create` and `load` through the MCP server, driven by Claude Code.

Known rough edges:

- The MCP server's `todoist_list` returns its records as an array in `structuredContent`, which the MCP specification does not allow, so schema-validating clients such as Claude Code reject the result. `todoist_load` and the SDKs are not affected.
- In TypeScript, the create input types (`TaskCreateData`, `ProjectCreateData`, ...) require every field the API's response marks as required, including ones the server assigns, such as `id` and `added_at`. Doist's definition marks nearly every response field required, so a plain `create({ content })` does not type-check; cast the argument as the example above does. `ProjectCreateData` also lists the list page's `next_cursor` and `results`, because Todoist's project record is a union of personal and workspace projects. The requests themselves work (verified live).
- Workspace, folder and billing endpoints are generated but not exercised: they need a Business plan, and writes to them are excluded from the live tests.
- The generated live suites do not pass in full against Todoist. Each failure is classified in [REPORT.md](REPORT.md), which also covers the developer experience of building this SDK.

## Entities, not endpoints

This SDK exposes the API as **34 semantic entities** that you
call directly, instead of assembling URL paths and query strings. See the [Entities](#entities) table below for the full list. Entities are
**Capitalised** to mark them as the primary surface, each with the operations they
support (`list`, `load`, `create`, `update`, `remove`):

```ts
const client = new TodoistSDK()
const items = await client.Activity().list()
```

Thinking in entities keeps the mental model small — for people and AI agents alike —
rather than reasoning about raw HTTP routes and query parameters.

## Offline unit testing

Every SDK ships a built-in **test mode** that swaps the HTTP transport for
an in-memory mock, so your unit tests run fully offline — no server, no
network, and no credentials:

### TypeScript

```ts
// The offline mock starts EMPTY — seed it with the records the test needs.
// Shape: { entity: { <entity-name>: { <id>: <record> } } }
const client = TodoistSDK.test({
  entity: {
    activity: {
      test01: { id: 'test01' },
    },
  },
})
const activitys = await client.Activity().list()
// activitys is an array of Activity entities, one per mock record
console.log(activitys.map((activity) => activity.data()))
```

### Python

```python
client = TodoistSDK.test()
activitys = client.Activity().list()
print([item.data_get() for item in activitys])
```

### Golang

```go
client := sdk.Test()
result, err := client.Activity(nil).List(
    nil, nil,
)
```

```json

      "command": "/abs/path/to/todoist-mcp"
    }
  }
}
```

## Direct and prepare

For endpoints the entity model doesn't cover, use the low-level methods:

- **`direct(fetchargs)`** — build and send an HTTP request in one step.
- **`prepare(fetchargs)`** — build the request without sending it.

Both accept a map with `path`, `method`, `params`, `query`,
`headers`, and `body`. See the [How-to guides](#how-to-guides) below.

## Advanced

> Everyday use only needs the sections above. This explains the internals
> behind every call — relevant when writing custom features.

Every SDK call runs the same five-stage pipeline:

1. **Point** — resolve the API endpoint from the operation definition.
2. **Spec** — build the HTTP specification (URL, method, headers, body).
3. **Request** — send the HTTP request.
4. **Response** — receive and parse the response.
5. **Result** — extract the result data for the caller.

A feature hook fires at each stage (e.g. `PrePoint`, `PreSpec`,
`PreRequest`), so features can inspect or modify the pipeline without
forking the SDK.

## Customizing this SDK

This repository contains its own generator (`.sdk/`), so the SDK is
customizable without forking any upstream tool:

- **The model** (`.sdk/model/`) declares everything this project owns:
  package names, versions, active features, per-target settings. It is
  written in [aontu](https://aontu.dev), a JSON-based
  specification language designed for building ontologies: easy to edit
  by hand, and files unify rather than override, so small declarations
  compose into one model. Regeneration re-reads it every time.
- **Templates** (`.sdk/tm/`) and **components** (`.sdk/src/cmp/`) are
  the two layers of generation, copied into this repo: templates are the
  literal per-language source, components generate the API-shaped parts.
- **Regeneration overwrites.** Each run rewrites every generated file from
  the model, the templates and the components, so an edit made to
  generated output is lost. Say what this project needs in its own model
  (`.sdk/model/sdk.aontu`), or extend a target with a component of its
  own in `.sdk/src/cmp/<target>/`, registered with `registerComponent`,
  which `voxgig-sdkgen doctor` reports as an addition rather than drift.
- **Custom features and entire custom targets** arrive through sdkgen
  packages (`voxgig-sdkgen package add`), on the same rails as the
  bundled languages, and `voxgig-sdkgen doctor` reports any drift from
  what a resync would write.

How-to: [customize and propagate templates](https://github.com/voxgig/sdkgen/blob/main/docs/how-to/customize-and-propagate-templates.md).
The full story: [voxgig.com/sdk/custom](https://voxgig.com/sdk/custom).
